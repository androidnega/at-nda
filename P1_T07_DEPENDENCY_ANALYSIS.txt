EXECUTIVE SUMMARY
─────────────────
P1.T07 changes a single predicate inside one private-path method
(`ClassRepApiService::authenticate()` at line 75). The Bearer-token
branch above it is untouched, and the surrounding methods that build
response shapes (`legacyCoursesPayload`, `openSession`, `closeSession`,
`closeSessionById`, `extendSession`, `studentsPayload`,
`buildDashboard`, `buildStudentDetailPayload`) are unaffected.

**Recommendation: keep `validateApiPassword()` as a 3-line PUBLIC
delegator** that forwards to `PasswordPolicy::matches`. Rationale:
  - The method is declared `public` on a public service class.
  - It is unique in the inventory for this reason (every other
    helper migrated in P1.T03–T06 was `private`).
  - Static search finds zero external callers TODAY, but deleting a
    public method on a long-lived service breaks ABI for any
    not-yet-merged branch, untracked admin script, or future
    controller. The cost of the shim is 3 lines.

A clean cut (Option B below) is technically defensible because the
static search is exhaustive within the repository, but it carries
non-zero ABI risk that the delegator eliminates for the price of three
lines of obvious code.

7. BACKWARD COMPATIBILITY RISKS
─────────────────────────────────────────────────────────────────────────

  CATEGORY A — Predicate behaviour
  ────────────────────────────────
  Risk:    PasswordPolicy::matches behaves differently from
           validateApiPassword.
  Reality: Bit-identical during the migration window
           (AUTH_ALLOW_LEGACY_PLAINTEXT=true). Same outcomes
           everywhere. After the post-rehash flip, plaintext rows
           lose access uniformly — the intended Phase 1 outcome.
  Severity: NONE.

  CATEGORY B — ABI risk (the headline question)
  ─────────────────────────────────────────────
  Risk:    `validateApiPassword` is PUBLIC. Deleting it could break
           any external caller that the static search did not see.
  Reality: Static search of the entire repository (app/, tests/,
           resources/views/, at-end_frontend_app/) finds NO external
           caller. But the method is on a public service class
           registered in the container — any caller via app(), DI
           injection, or method reflection in code we do not own
           (vendor packages, hot-fix scripts, generated code) would
           snap.
  Severity: LOW with delegator (Option A) — fully eliminated.
           LOW-to-MEDIUM with clean delete (Option B) — depends on
           whether you trust the repo-wide static search to be the
           complete universe of callers.

  CATEGORY C — Response shape
  ───────────────────────────
  Risk:    Wire contract drift.
  Reality: P1.T07 leaves response()->json(['message' => 'Invalid credentials'], 401)
           bit-identical. Every other response method is untouched.
  Severity: NONE.

  CATEGORY D — Flutter contract
  ─────────────────────────────
  Risk:    Flutter screens read keys that disappear or rename.
  Reality: Flutter never references the string "validateApiPassword".
           The success-path keys (is_class_rep, courses, session,
           students[], dashboard) come from untouched methods.
  Severity: NONE.

  CATEGORY E — Web blade
  ──────────────────────
  Risk:    A blade view AJAX-fetches /api/rep/* or /api/class-rep/*.
  Reality: Zero blade references found.
  Severity: NONE.

  CATEGORY F — Race / state
  ─────────────────────────
  Risk:    PasswordPolicy::matches is a pure function; removing
           the helper could alter call ordering.
  Reality: PasswordPolicy::matches has no DB I/O and no model events.
           Order of operations in authenticate() remains identical:
           Bearer first → (if absent) validate request → Student
           lookup → PREDICATE → isClassRep gate → return.
  Severity: NONE.

  CATEGORY G — Operational / audit / log alerts
  ─────────────────────────────────────────────
  Risk:    Internal grep / log alert keys off the method name.
  Reality: No matches in logs/, app/Console/, bootstrap/, or
           config/ for the string "validateApiPassword".
  Severity: NONE.


─────────────────────────────────────────────────────────────────────────
DECISION RECOMMENDED — DELEGATOR (Option A)
─────────────────────────────────────────────────────────────────────────

  Recommendation: replace the body of validateApiPassword() with a
  3-line delegator, keep the PUBLIC method signature intact.

  Proposed replacement:

      public function validateApiPassword(string $input, ?string $stored): bool
      {
          return PasswordPolicy::matches($input, (string) $stored);
      }

  Why:
    - This is the ONLY public-helper occurrence in P1_PASSWORD_USAGE_INVENTORY
      (every other migrated helper in P1.T03–T06 was private).
    - Cost of the shim is three lines.
    - Eliminates ABI risk for callers the static search cannot see
      (vendor packages, ops scripts, future controllers in flight).
    - Matches the Phase 1 spec verbatim.
    - Future-proof: once it is confirmed safe to delete (or once
      Phase 3 deprecates the index+password endpoints entirely),
      the shim can be removed cleanly in a one-line patch.

  Alternative — clean delete (Option B):
    - Saves three lines of code.
    - Risks unseen external callers (estimated LOW based on the
      static search, but non-zero).
    - Inconsistent with the Phase 1 spec recommendation.
    - Could be deferred to Phase 3 alongside the broader
      index+password deprecation.

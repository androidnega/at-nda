Compatibility A — 5 MB upload cap from P1.T16
---------------------------------------------------------------
  P1.T16 rejects raw image bytes > 5 MB inside
  Student::profileImageDimensionsAcceptable(). This is the MODEL-level
  ceiling. PHP can enforce its own ceilings BEFORE control ever
  reaches PHP code, so all four upload paths must be re-checked
  against the runtime ini values:

  Path A — Web multipart (StudentDashboardController, profile_photo)
    Validation rule today : image|mimes:...|max:10240  (10 MB)
    PHP-tier ceiling here : min(upload_max_filesize=2M, post_max_size=8M) = 2 MB
    Model-tier ceiling    : 5 MB (after T16)
    Effective ceiling     : 2 MB on this dev box (FPM truncates).
                            ⇒ The T16 guard would only be reachable
                              for files in the 2-5 MB band on a host
                              whose php.ini permits it.
    Production reality    : cPanel hosts typically ship
                              upload_max_filesize=64M
                              post_max_size=64M
                            ⇒ T16's 5 MB guard becomes the binding
                              constraint there, as intended.

  Path B / C / D — base64 data URLs (onboarding + profile update)
    Validation rule today : profile_image: string (no length cap)
    PHP-tier ceiling here : post_max_size=8M for the entire request body
    Base64 inflation      : binary → base64 ≈ 1.37×
    Effective raw cap     : ~5.8 MB binary fits in 8M post_max_size
                            (after the "data:image/jpeg;base64," prefix
                             plus the rest of the form fields).
    Model-tier ceiling    : 5 MB (after T16)
    Effective ceiling     : 5 MB (T16) on this dev box AND on prod.
                            ⇒ T16 binds correctly for the base64 paths.

  Verdict A — COMPATIBLE in principle.
  -------------------------------------------------------------------
  The T16 model-level 5 MB cap is the binding constraint on every
  production-grade host (upload_max_filesize ≥ 5M, post_max_size ≥ 8M).
  On this dev box the multipart path is FPM-truncated at 2 MB; the
  base64 paths are FPM-truncated at ~5.8 MB raw which still lets T16
  do its job.

  Operator runbook addendum BEFORE P1.T16 ships
  -------------------------------------------------------------------
    1. Verify production php.ini on each FPM pool:
         php -r 'echo "upload=".ini_get("upload_max_filesize"),
                      " post=".ini_get("post_max_size"),"\n";'
       Both should report ≥ 5M (recommend ≥ 8M for headroom).
    2. If either is lower, the operator must:
         - raise upload_max_filesize to at least 8M
         - raise post_max_size to at least 10M
         - restart PHP-FPM
       Without this, well-formed 4-5 MB uploads will silently fail
       with a 413 / "POST data exceeded" BEFORE Laravel sees them.
    3. The model-level 5 MB cap (T16) is intentionally LOWER than
       these ini values so the application can return a clean
       422 envelope rather than a webserver-level 413.


Compatibility B — 60-second queue timeout from P1.T15
---------------------------------------------------------------
  P1.T15's job declares:
    public int $timeout = 60;
  This timeout is enforced by Laravel's queue worker via pcntl_alarm()
  (SIGALRM). It is NOT enforced by PHP's max_execution_time ini.

  CLI (queue worker) runtime budget on this box
    max_execution_time = 0   ⇒ unlimited; Laravel manages timing.
    memory_limit       = 128M ⇒ comfortable headroom (see below).
    max_input_time     = -1   ⇒ not relevant; worker reads from DB.

  Worst-case worker memory footprint after T16 lands
    Laravel framework load    : ~30-40 MB
    Student::find($id) + save : ~2 MB (single row + relation load)
    Raw bytes read from disk  : ≤ 5 MB
    GD true-color canvas      : 1280 × 1280 × 4 = ~6.5 MB
    JPEG encode buffer        : ~1-2 MB
    -----------------------------------------------------------------
    Total                     : ~50 MB
    Available                 : 128 MB
    Headroom                  : 78 MB (~60% slack)

  Worst-case worker CPU time per job
    A 1280×1280 GD resize on a modern CPU completes in well under
    one second; the 10-pass quality loop bounded to 500 KB rarely
    exceeds 3 seconds even on slow shared hosts. The 60 s job
    timeout has ~20× safety margin.

  cPanel CLI typical values
    memory_limit       : 256M (more headroom than this dev box)
    max_execution_time : 0    (CLI default — Laravel still manages it)
  ⇒ Production environment exceeds dev-box capacity. No concerns.

  Verdict B — COMPATIBLE.
  -------------------------------------------------------------------
  The 60 s queue timeout is enforced by Laravel itself, independent
  of php.ini. The CLI's unlimited max_execution_time is exactly the
  right default. Memory headroom is ~60% on this dev box and even
  larger on a typical cPanel CLI. The job will complete in seconds
  on real images; the 60 s ceiling is for malicious / corrupted
  edge cases.

  1. Api/NotificationsController       — POST /api/notifications/pending
  2. Api/StudentProfileController      — POST /api/student/profile + /api/update-profile

because line 1165 still uses Hash::make() for the "set password" flow
(a different operation that PasswordPolicy does not cover).

RISKS
─────────────────────────────────────────────────────────────────────────

  1. Migration-window dependency. Every behavioural assumption above
     is conditioned on AUTH_ALLOW_LEGACY_PLAINTEXT remaining true
     during the rehash window. After the operator runs
     `php artisan students:rehash-passwords` (P1.T02) and flips the
     flag to false, plaintext rows lose access across ALL of:
       - api/login                                 (P1.T03)
       - api/attendance/sync + missed-warnings     (P1.T04)
       - api/sessions/active (missed-warning sub-path)
         + api/sessions/{id}/location              (P1.T05)
       - api/class/active-session + api/session/{id}/stats
                                                   (P1.T06)
       - api/rep/*  +  api/class-rep/*             (P1.T07)
       - api/notifications/pending                 (this commit)
       - api/student/profile  +  api/update-profile (this commit)
       - api/v1/auth/login                          (this commit)
       - api/device-token                           (this commit)
       - WEB POST /student/login/password           (this commit)
     This uniform behaviour is THE INTENDED outcome of Phase 1.

  2. StudentDashboardController is now in the password stack. It
     was missed by the original master guide (it uses inline
     Hash::check rather than a private helper, so it didn't show up
     in helper-based searches) and was added by the inventory I
     produced before P1.T03. Including it in this commit closes the
     last student-login gap.

  3. NotificationsController response uses 'success' boolean keys
     that differ from the rest of the API (which uses 'status' or
     bare keys). This pattern is preserved unchanged — no shape
     normalisation in this commit.

  4. V1/AuthController structured logging emits student_id on
     failed login. This was already part of the v1 contract before
     this commit and is preserved unchanged. Note: this is
     structured (JSON), so it does not leak via plain greppable
     access logs; it lands in the same log channel as other
     api.v1.* events.

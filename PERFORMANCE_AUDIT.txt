PART 0 — TL;DR  (read this first)
--------------------------------------------------------------------------------
Your app is currently configured so that EVERY web request hits MySQL for at
least three framework things (session, cache, cache lock), and one
POST /api/attendance executes 8–15 SQL statements plus a row-level lock on
`cache_locks`. With APP_DEBUG=true and LOG_LEVEL=debug the app also writes a
verbose entry into a single `laravel.log` file for every request.

Under simultaneous attendance marking (say 100 students in 30 seconds) this
turns your single MySQL instance into a serialised queue: row locks on
`cache_locks` + `sessions` + `attendances` pile up, PHP-FPM workers wait on
those locks, cPanel sees the workers as "stuck" Entry Processes, and the
account hits the EP / I/O / memory cap. Result: HTTP 508 "Resource Limit Is
Reached" or 503 from LiteSpeed/Apache, and slowness for everyone else.

The root cause is NOT a missing CPU/RAM upgrade. It is a stack of small
problems that compound:

  1. Session, Cache, Queue, AND distributed Lock are ALL on MySQL.
  2. The student lookup uses `whereRaw('UPPER(TRIM(index_number)) = ?', ...)`
     which DEFEATS the unique index on `index_number` (full table scan).
  3. `/api/sessions/active` does an N+1 query per session for "already_marked"
     plus per-session `loadMissing(...)` re-runs.
  4. The QR-rep page polls `/session/{id}/stats` every 15s AND rotates the QR
     image every ~8s; the Flutter rep page polls `/rep/courses` every 8s.
  5. APP_DEBUG=true + LOG_LEVEL=debug in production = a ~1–5 KB log entry
     written on every request to a single growing file (I/O wait + disk fill).
  6. `attendance_sessions` has no index on `is_active`, `qr_token`,
     `attendance_week_id`, `class_id`, or the (course_id,is_active,end_time)
     hot path. Every "active session for course/class" query scans more rows
     as session history grows.

The good news: ~80% of the slowness goes away with FILE-based session/cache
(no Redis required) + 3 production .env flags + 5 SQL indexes + one
N+1 fix. Detailed plan in PART 8.

5.2  Concrete query problems (file:line references)

  [A] N+1 in /api/sessions/active
      File: app/Services/ActiveSessionListBuilder.php
      Lines 129–169   `buildRows()`
      For EVERY session in the response it does:
          Attendance::query()->where('student_id', ...)
                             ->where('attendance_session_id', ...)
                             ->first();
      If a student has 5 active sessions, that's 5 separate queries just
      for "already_marked". Combined with the per-poll repeat from the
      Flutter app and the rep page, this is your single biggest read
      amplifier. Fix in PART 8 item 7.

  [B] Non-SARGable student lookup (full table scan)
      Files:
        app/Models/Student.php                    L213, L219
        app/Http/Controllers/Api/AttendanceController.php  L75
        app/Http/Controllers/Api/SessionController.php     L185
        ...and at least 14 other call sites
      Code:
          Student::whereRaw('UPPER(TRIM(index_number)) = ?', [$indexUpper])->first();
      Because `index_number` is wrapped in UPPER(TRIM(...)), MySQL CANNOT
      use the unique index on that column. Every login + every mark-attendance
      scans the full `students` table. With 5,000 students that's still fast;
      with 50,000 it gets visible; under contention it's a disaster because
      every full scan also takes a shared lock on the secondary index.
      Since Student::saving() already uppercases the column on write, the
      stored value is ALWAYS uppercased — UPPER/TRIM are unnecessary.
      Fix: replace with `Student::where('index_number', $indexUpper)->first()`
      or use `whereRaw` only as a FALLBACK after the indexed lookup misses.
      Fix in PART 8 item 4.

  [C] N+1 in isClassRepForCourse()
      File: app/Models/Student.php, L638–L652
      Calls Course::find(), then loops `assignedClassIds()` and runs
      `classReps()->where('class_id', $classId)->exists()` per id. Called
      twice in markAttendance (once for the early "rep cannot mark"
      check, once inside resolveSession). Cache result per request.

  [D] AttendanceFraudGuard::detectCollision runs TWO unbounded queries
      File: app/Services/AttendanceFraudGuard.php, L83–L127
      Both queries filter by device_fingerprint AND week / session. With
      the existing indexes they're fine NOW, but you should add:
          INDEX attendances (attendance_week_id, device_fingerprint)
      so the "same week, different student" query stops scanning the
      session index.

  [E] resolveSession uses LOWER(session_code) in a fallback
      File: app/Http/Controllers/Api/AttendanceController.php, L747
          ->whereRaw('LOWER(session_code) = ?', [strtolower($code)])
      Same SARGable problem as Student. Since `session_code` is generated
      uppercase (`AttendanceSession::generateUniqueSessionCodeForCourse`),
      the fallback is hit only by user-typed lowercase codes. Either store
      a `session_code_upper` generated column with an index, OR force
      uppercase on input and drop the fallback.

  [F] /api/sessions/active does TWO bulk UPDATEs every poll
      File: app/Http/Controllers/Api/SessionController.php, L26–L33
          AttendanceSession::deactivateExpiredSessions();   // UPDATE
          AttendanceSession::query()
              ->where('attendance_mode', 'checkin_checkout')
              ...->update(['checkout_enabled' => true]);     // UPDATE
      These are WRITE queries hidden inside a READ endpoint that is
      polled by every student device + by the rep page every 8s. On a
      busy class with 200 phones polling, that's ~25 UPDATE statements
      PER SECOND on `attendance_sessions` even when nothing has changed.
      Move both into a 1-minute scheduled job (artisan schedule) so the
      poll endpoint is read-only.

  [G] Course::studentMayAttend() touches the pivot every call
      File: app/Models/Course.php, L182–L185 + L152–L163
      `assignedClassIds()` either hits `schoolClasses()->pluck()` (one
      query) or returns a cached array. Wrap the result in a static
      per-request memo keyed by course id.

  [H] SystemSetting::get() already has TWO layers of caching (per-request
      memo + 60 s Cache::remember). Good. But it relies on
      `Cache::remember('atenda:system_settings:row', 60s, ...)` — which
      means with CACHE_STORE=database, the FIRST request per minute
      writes a row to `cache` and every subsequent request reads it.
      Switching CACHE_STORE to `file` (PART 8 item 1) makes this
      essentially free.

5.3  Heavy joins / full scans elsewhere
  ▶ Course::resolvedLecturerName()  (Course.php L85+) runs up to 3 joins

PART 6 — Attendance Workflow Audit  (POST /api/attendance)
--------------------------------------------------------------------------------
File: app/Http/Controllers/Api/AttendanceController.php  markAttendance()
Per request, assuming the happy "QR + geofence" path, here is the actual
sequence of SQL/IO calls:

   #   Operation                                         Where
   1   SELECT * FROM sessions WHERE id=?                  Laravel session driver
   2   UPDATE sessions SET payload=?, last_activity=?     end of request
   3   SystemSetting::get()  → SELECT FROM cache          DB cache (first call/min)
   4   SELECT students WHERE UPPER(TRIM(index))=?         FULL SCAN (problem B)
   5   (optional) SELECT students WHERE bound_ip=?
   6   SELECT courses WHERE id=?
   7   SELECT attendance_sessions WHERE id=? (or token)
   8   SELECT courses WHERE id=?                          (re-fetch via relation)
   9   isClassRepForCourse  → 1+N queries (problem C)
   10  studentMayAttend → assignedClassIds → pivot query
   11  validateSessionGeofence (pure PHP, no SQL)
   12  SELECT attendances WHERE student_id=? AND session_id=?  (duplicate check)
   13  AttendanceFraudGuard::detectCollision → 1–2 SELECTs
   14  AttendanceMarkLock::run
         ├── INSERT INTO cache_locks ...                 (row lock)
         └── DELETE FROM cache_locks WHERE key=?
   15  firstOrCreate(attendances) → 1 SELECT + 1 INSERT
   16  AuditLogService::record → 1 INSERT INTO audit_logs
   17  SELECT COUNT(*) attendances WHERE session_id=? AND status='present'
   18  event(SessionLiveEvent) → with broadcast=log: 1 log write
                                  with broadcast=reverb (queued): 1 INSERT
                                                                  INTO jobs
   19  UPDATE sessions (Laravel session shutdown)

Total: ~12–18 DB statements + 1–2 file writes (log + cookie) per mark.
With 100 simultaneous marks that's 1,200–1,800 statements arriving in a
1–2 second window, plus 100+ row locks on `cache_locks` and `sessions`.
A single shared MySQL with `innodb_buffer_pool_size` of ~256 MB (typical
on shared cPanel) starts queuing transactions; the PHP-FPM pool fills up;
LiteSpeed/Apache start returning 508.

Observations:

  ✓ You ALREADY have a per-(session, student) cache lock — good idea.
  ✗ But the lock is in MySQL, which makes it WORSE than no lock under
    high contention: two concurrent requests for two DIFFERENT students
    still serialise on InnoDB metadata for the `cache_locks` table.
    With CACHE_STORE=file, the lock becomes a flock() on a tiny file
    and contention disappears.
  ✓ You ALREADY have a UNIQUE (student_id, attendance_session_id)
    constraint, so duplicate marks are physically impossible regardless
    of the lock — the lock is purely there to suppress the
    QueryException noise. You can even DROP the lock and rely on the
    unique + a try/catch for QueryException 23000.
  ✗ The SystemSetting::get() static memo is reset between requests, so
    each request still pays for one Cache read.
  ✗ The `present_count` SELECT (step 17) runs even when nobody is
    listening for broadcasts (BROADCAST_CONNECTION=log).
    Guard with: `if (config('broadcasting.default') !== 'log') { ... }`.
  ✗ The Reverb broadcast is queued (ShouldBroadcast), so it writes a
    job row even when nobody is consuming the queue. Either run a queue
    worker, or set BROADCAST_CONNECTION=log (already done — good),
    or switch the event to ShouldBroadcastNow ONLY when Reverb is
    confirmed running, OR add `should_queue: false` env-driven branch.

Notifications / images / GPS observations:
  • The endpoint does NOT trigger any external notification (FCM is
    referenced in env but not wired into mark-attendance — good).
  • The endpoint does NOT store any image; only lat/lng floats and
    a small client_meta JSON (<1 KB). Storage I/O is not a concern for
    marking; it IS a concern for profile-image uploads (see PART 9).

PART 8 — Optimisation Plan  (Redis NOT required)
--------------------------------------------------------------------------------

LEGEND
  Impact:   ★★★ huge / ★★ medium / ★ small
  Effort:   ▲ low (minutes) / ▲▲ medium (1–2 h) / ▲▲▲ high (refactor)

──────────────────────────────────────────────────────────────────────
TIER A — High impact, low effort  (do these TODAY)
──────────────────────────────────────────────────────────────────────

  1.  [SH] [★★★ / ▲]  Move Cache, Session, and Lock off MySQL onto FILE.
      Edit production .env:
          CACHE_STORE=file
          SESSION_DRIVER=file
      Why: removes the row-locking arms-race on `cache_locks` and
      `sessions` for every request. File locks (flock) on local disk are
      ~10× cheaper than MySQL row locks AND don't block other requests.
      No Redis required. Then:
          php artisan config:clear && php artisan cache:clear
          php artisan optimize
      Expected gain: typically -60% p95 latency under contention,
      and faults on `ep` should drop to near zero.

  2.  [SH] [★★★ / ▲]  Production .env hygiene.
          APP_ENV=production
          APP_DEBUG=false
          LOG_LEVEL=warning
          LOG_STACK=daily
          LOG_DAILY_DAYS=7
      Then:
          php artisan config:cache
          php artisan route:cache
          php artisan view:cache
          php artisan event:cache
      Why: APP_DEBUG=true forces Laravel to load the Whoops error
      handler, register a query log, and re-resolve config on every
      request. config:cache + route:cache alone typically remove 30–80 ms
      per request on shared hosting (no opcache).

  3.  [SH] [★★★ / ▲]  Enable OPcache.
      cPanel → "Select PHP Version" → Extensions → tick `opcache`.
      Recommended INI (cPanel → "MultiPHP INI Editor" → Editor mode):
          opcache.enable=1
          opcache.enable_cli=0
          opcache.memory_consumption=128
          opcache.max_accelerated_files=20000
          opcache.validate_timestamps=1     ; (set to 0 + use deploy cache:clear
                                            ;  for max speed on a VPS)
          opcache.revalidate_freq=2
      Why: PHP without OPcache reparses every .php file on every request.
      With Laravel that's 800–1,500 files = 200–400 ms of pure parsing
      per request. OPcache is free, ships with PHP 8.3, and is the
      single biggest speedup you can get without writing code.
      Expected gain: -30 to -60% on every endpoint.

  4.  [SH] [★★ / ▲]  Fix the non-SARGable student lookup (4–5 LOC change).
      In app/Models/Student.php::findByIndex() and in every controller
      that uses `whereRaw('UPPER(TRIM(index_number)) = ?', ...)`,
      replace with:
          Student::where('index_number', strtoupper(trim($indexNumber)))->first();
      Falls back to the existing whereRaw only when the fast path
      returns null. Saves 1 full table scan per login + per mark.
      Expected gain: as your student count grows past ~10k rows, this
      single change is the difference between a 20 ms and a 200 ms
      lookup.

  5.  [SH] [★★ / ▲]  Add the 7 missing indexes from PART 5 §5.4.
      Pure additive — safe to run during a low-traffic window via a
      Laravel migration. Each CREATE INDEX takes <5 s on a 100k-row
      table.

  6.  [SH] [★★ / ▲]  Move the two UPDATE statements out of
      `/api/sessions/active` (PART 5 [F]) into the scheduler:
          app/Console/Kernel.php  (or routes/console.php)
              $schedule->call(fn () =>
                  AttendanceSession::deactivateExpiredSessions()
              )->everyMinute();
              $schedule->call(/* enable checkout on expected_end_time */)
                       ->everyMinute();
      Then add ONE cron line in cPanel → Cron Jobs:
          * * * * * cd /home/USER/public_html && /usr/local/bin/php artisan schedule:run >> /dev/null 2>&1
      Expected gain: removes ~25 UPDATE statements per second during
      peak polling.

──────────────────────────────────────────────────────────────────────
TIER B — High impact, medium effort  (do this WEEK)
──────────────────────────────────────────────────────────────────────

  7.  [SH] [★★ / ▲▲]  Kill the N+1 in ActiveSessionListBuilder::buildRows.
      Before the foreach loop, fetch all "my attendances" in ONE query:
          $myAttendances = $student
              ? Attendance::query()
                  ->where('student_id', $student->id)
                  ->whereIn('attendance_session_id', $sessionIds)
                  ->get()
                  ->keyBy('attendance_session_id')

      Expected gain: turns N+1 → 2 queries. With 5 active sessions and

  8.  [SH] [★★ / ▲▲]  Memoise isClassRepForCourse + assignedClassIds.
      Both functions are called repeatedly within a single request.
      Add a static per-request cache keyed by course/student id (see

PART 9 — Final Output

ROOT CAUSE ANALYSIS  (the why, in one paragraph)

  The application stack is configured for a single-server development
  workstation, not for a shared cPanel host under concurrent load. Every
  HTTP request causes 3 writes to MySQL just for framework plumbing
  (session, cache lookup, cache lock); a single attendance POST causes
  12–18 SQL statements; and the polling endpoints (`/api/sessions/active`,
  `/session/{id}/stats`, `/sessions/current-qr/{id}`) do hidden writes
  and N+1 reads. Multiplied by 100+ concurrent students this exceeds
  the cPanel Entry-Process / I/O / connection ceilings, which surface
  as "Resource Limit Is Reached" or 503/508 responses. APP_DEBUG=true,
  LOG_LEVEL=debug, OPcache likely off, and APP_ENV=local are amplifiers.

TOP 5 BOTTLENECKS  (in measured order of pain)

  1. CACHE_STORE=database  +  SESSION_DRIVER=database
        → row-lock contention + heavy writes per request.
  2. APP_DEBUG=true + LOG_LEVEL=debug + APP_ENV=local
        → no opcache benefit, huge log writes, no config caching.
  3. N+1 in /api/sessions/active for `already_marked` per session.
  4. Non-SARGable Student lookup (UPPER/TRIM defeats unique index).
  5. /api/sessions/active running TWO UPDATEs on every poll.

EXACT FIXES IN PRIORITY ORDER  (copy-paste this checklist)

WHICH FIXES NEED A VPS?

  • Anything in TIER E (item 19, 20).
  • Running `php artisan reverb:start` 24/7 (cPanel "Application Manager"
    can sometimes do this on LiteSpeed hosts, but most shared accounts
    kill long-running processes — VPS is far safer).
  • Supervised `php artisan queue:work` daemon. (You can fake-it on
    shared via cron-driven `queue:work --max-time=55 --stop-when-empty`
    every minute, but it's fragile.)
  • Redis. Most shared cPanel plans do NOT offer Redis. If yours does
    (e.g. CloudLinux + Redis add-on, or a managed Redis URL like Upstash
    free tier), then RedisRuntimeConfig in your code will pick it up
    from the system_settings UI without redeploying — see
    app/Support/RedisRuntimeConfig.php which already does auto-discovery
    of REDIS_URL, REDIS_HOST and localhost:6379.

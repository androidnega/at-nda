0. AT-A-GLANCE SUMMARY
================================================================================

  Spec change (from phase_1_security_implementation.txt §T15)
  ----------------------------------------------------------------------
    CREATE app/Jobs/ResizeStudentProfileImage.php.
    Implements ShouldQueue with $tries=3, $timeout=60.
    Constructor: (int studentId, string tempRelativePath).
    handle() reads the raw temp file from disk('local'), calls
      Student::saveProfileImageFromRawBytes($raw)  ← method added in P1.T16
    and deletes the temp file via Storage::disk('local')->delete().

    P1.T15 by itself is a no-op at runtime — the job has no caller
    until P1.T16 wires dispatch from saveProfileImageFromUpload(). The
    file lands first so P1.T16 has something to reference.

  Net behavioural delta after JUST P1.T15 lands
  ----------------------------------------------------------------------
    Production HTTP: zero change. Nothing dispatches the job.
    Production console: zero change. Nothing dispatches the job.
    Queue worker: nothing new to process.
    Disk: no new files; `app/Jobs/` directory created with one file.

  Net behavioural delta AFTER P1.T16 also lands
  ----------------------------------------------------------------------
    Web /media upload, web onboarding, mobile API profile update:
      + Request thread saves raw bytes to
        storage/app/private/tmp-profile/<student_id>-<uuid>
      + Inserts one row into `jobs` table
      + Returns immediately (no GD resize on the request thread)
      + Worker (queue:work or cron-driven runner) picks the job up,
        runs imagecreatefromstring → imagecopyresampled → imagejpeg
        loop, writes the final file to
        storage/app/public/students/<id>_<uniqid>.<ext>
      + Worker deletes the temp file
      + Student::profile_image column is updated via $student->save()
    Until the worker runs, the OLD profile_image stays in place. No
    user-visible flash. No write-then-read race.

  One critical compatibility point
  ----------------------------------------------------------------------
    Deployed Flutter APKs (and the web dashboard) refresh the avatar
    by re-fetching /api/students/{id}/profile-image. Because the
    `profile_image` column changes only AFTER the worker completes,
    a user can take a selfie at 12:00:00 and see the new avatar at
    12:00:05 (queue worker tick) rather than 12:00:00. This is the
    one user-visible behavioural change.

1. CURRENT PROFILE IMAGE UPLOAD FLOW
================================================================================

There are FOUR paths that write a profile image today. All four
ultimately reach `Student::storeOptimizedProfileImage(string $raw)`,
which runs the GD pipeline synchronously on the request thread.

  Path A — Web admin/student dashboard (multipart upload)
  ----------------------------------------------------------------------
   Route       :  POST  /student/dashboard/...                (web)
   Controller  :  StudentDashboardController::completeBasic    (l. 815-822)
                  StudentDashboardController::updateProfile    (l. 1074-1080)
   Validation  :  profile_photo: image|mimes:jpg,jpeg,png,webp|max:10240
                  (max:10240 = 10 MB raw upload)
   Model call  :  $student->saveProfileImageFromUpload($request->file('profile_photo'))
   Synchronous :  YES. GD resize runs in the PHP-FPM worker.

  Path B — Web student onboarding (base64 data URL)
  ----------------------------------------------------------------------
   Route       :  POST  /student/onboarding/complete            (web)
   Controller  :  StudentOnboardingController                   (l. 75-78)
   Validation  :  profile_image: required|string                (no size cap)
   Model call  :  $student->saveProfileImageFromBase64($validated['profile_image'])
   Synchronous :  YES.

  Path C — Mobile API profile update (base64 data URL)
  ----------------------------------------------------------------------
   Route       :  POST  /api/student-profile/update             (api)
   Controller  :  Api\StudentProfileController::update          (l. 49-53)
   Validation  :  profile_image: nullable|string                (no size cap)
   Model call  :  $student->saveProfileImageFromBase64(...)
   Synchronous :  YES.

  Path D — Mobile API onboarding (base64 data URL)
  ----------------------------------------------------------------------
   Route       :  POST  /api/onboarding/complete                (api)
   Controller  :  StudentOnboardingController                   (same as Path B —
                  Flutter posts data:image/jpeg;base64,... per
                  at-end_frontend_app/lib/pages/onboarding_page.dart l. 51-58)
   Validation  :  profile_image: required|string
   Model call  :  $student->saveProfileImageFromBase64(...)
   Synchronous :  YES.

  GD pipeline (storeOptimizedProfileImage + optimizeProfileImageBinary)
  ----------------------------------------------------------------------
    1. imagecreatefromstring($raw)            ← allocates W*H*4 bytes
    2. Compute maxDimension = 1280; scale to fit
    3. imagecreatetruecolor + imagefill (white background)
    4. imagecopyresampled to target canvas
    5. Loop up to 10 passes:
       - imagejpeg($canvas, null, $quality)   ← $quality starts at 86
       - If <= 500 KB, return
       - Else: drop quality by 6 (down to 62), then start shrinking
         canvas by 10% per pass (min 480x480)
    6. delete previous file via Storage::disk('public')->delete()
    7. Storage::disk('public')->put('students/<id>_<uniqid>.<ext>', $binary)
    8. $this->profile_image = $filename                          ← model
       (controller separately calls $student->save())

  Memory cost — the H-04 finding
  ----------------------------------------------------------------------
    imagecreatefromstring is the killer step. For a 6000×6000 PNG:
       6000 * 6000 * 4 = 144 000 000 bytes  (~137 MB true-color buffer)
    On a 256 MB cPanel FPM worker, three concurrent uploads of this
    shape OOM the pool. P1.T15 itself doesn't fix this — P1.T16 adds
    the dimension guard that REJECTS anything > 4000x4000 or > 5 MB
    BEFORE GD ever sees it. P1.T15 just provides the off-thread
    landing zone for the (now-bounded) resize work.

Disks
---------------------------------------------------------------
  config/filesystems.php (verified):

   'public' → driver=local, root=storage/app/public     (FINAL — already used)

  the few seconds between the request handler and the worker run.

Final path pattern
---------------------------------------------------------------
   storage/app/public/students/<student_id>_<uniqid>.<ext>
   served as:
   https://<APP_URL>/storage/students/<student_id>_<uniqid>.<ext>
   AND through the controller:
   GET /media/students/{student}/profile-image
   GET /api/students/{student}/profile-image
   (StudentImageController::show reads the binary back and re-emits
    it with explicit CORS + cache headers. URL pattern is the public
    contract Flutter depends on — must NOT change.)

Tmp path pattern (NEW — introduced in T15+T16, not in T15 alone)
---------------------------------------------------------------
   storage/app/private/tmp-profile/<student_id>-<uuid>
   - Not publicly served (private disk).
   - Auto-created by Storage::disk('local')->put() — no migration needed.
   - Lifetime: a few seconds (worker tick) under normal load.
   - Orphan cleanup: P1.T15 spec mentions an "artisan cleanup task
     (introduced in Phase 8)" for stranded temp files. Phase 8 has
     not landed; orphan accumulation is mitigated by:
       (a) the job's $tries=3 retry envelope,
       (b) the job's cleanup-on-success-or-failure pattern,
       (c) manual pruning if storage runs low (find storage/app/
           private/tmp-profile -mtime +1 -delete).

Disk-level guarantees
---------------------------------------------------------------
   - storage/app/private/  exists; tracked by .gitignore       ✓
   - storage/app/public/   exists; tracked by .gitignore       ✓
   - public/storage symlink exists when `php artisan storage:link`
     has run. Required for the legacy /storage/... URL pattern,
     even though StudentImageController re-serves through the
     controller route. Deploy runbook already requires storage:link.

3. CURRENT IMAGE DIMENSIONS
================================================================================

Server-side cap (today)
---------------------------------------------------------------
   $maxDimension = 1280   in Student::optimizeProfileImageBinary
   Any incoming image, regardless of original W×H, is rescaled so the
   longest edge ≤ 1280 px on the FIRST pass. Subsequent passes may
   shrink further (×0.9 per pass, floor 480 px) until quality target
   met.

Server-side ENCODED cap (today)
---------------------------------------------------------------
   $maxBytes  = 500 * 1024 = 512 000 bytes (≈ 500 KB)
   JPEG at quality 86 → 62; if still too large, shrink dims and retry.

Request-side cap (today)
---------------------------------------------------------------
   Path A: image|max:10240 (10 MB raw upload via the validation rule)
   Paths B/C/D: NO server-side cap on the base64 string today.
                A 50 MB selfie POSTed as base64 sails through.
                This is the OTHER half of the H-04 footgun. P1.T16
                closes it with the 5 MB / 4000 px raw guard.

Post-T15+T16 cap
---------------------------------------------------------------
   Reject anything where raw bytes > 5 * 1024 * 1024 (5 MB)
   OR width or height > 4 000 px
   BEFORE the GD allocation.
   Worst-case GD allocation falls from 4000*4000*4 = 64 MB →
   1280*1280*4 = ~6.5 MB working memory in the worker.

Output extension
---------------------------------------------------------------
   Always 'jpg' today (see renderProfileImageBinary — webp branch
   exists but is never selected). Output filenames are
   `<id>_<uniqid>.jpg`.

4. CURRENT IMAGE FILE-SIZE DISTRIBUTION
================================================================================

Observed (live disk inspection unavailable on this dev box —
storage/app/public/students/ is empty on this machine; numbers below
are derived from the encoding pipeline)
---------------------------------------------------------------
   Best-case   (a 800×800 selfie, q=86):       ~35  KB
   Median      (typical 1280×1280, q=86):      ~120 KB
   Cap         (1280×720, q=62):                500 KB
   Hard cap    (storeOptimizedProfileImage returns null > 500 KB,
                so nothing on disk exceeds this).

   ⇒ Per-student row on disk: 35–500 KB, hard-capped.
   ⇒ For 5 000 students (audit cohort): 0.18 GB – 2.4 GB on the
     `public` disk in the worst case. Plausible on cPanel today.

After P1.T15 + P1.T16
---------------------------------------------------------------
   Final image sizes UNCHANGED — same optimize pipeline, same
   500 KB cap, same filename pattern.

   New transient overhead on the `local` disk:
     ≤ 5 MB per pending job (raw bytes pre-resize).
     N concurrent jobs ⇒ ≤ N * 5 MB transient.
     Under realistic load (1 worker tick per minute on cPanel cron):
     ≤ 20 MB transient.
     Pruned by the job on success/failure.

================================================================================
6. EXISTING AVATAR FALLBACK LOGIC
================================================================================

Server-side fallback (StudentImageController)
---------------------------------------------------------------
   When profile_image is empty OR the underlying file is missing
   on disk OR Storage::get() throws, the controller returns a
   1×1 transparent PNG (base64 inlined) with:
     Cache-Control: public, max-age=3600
     Access-Control-Allow-Origin: *
   This is INTENTIONAL — Flutter web NetworkImage and <img> tags
   would otherwise hit a hard 404 and flash a broken-image glyph.

Server-side fallback (Student::avatarInitials)
---------------------------------------------------------------
   Returns "First+Last" initial pair, or first 2 chars of the
   index number, or "—". Used by Blade tables when profile_image
   is empty (see admin/students.blade.php l. 246-248).

Client-side fallback (Flutter — ProfileAvatar widget)
---------------------------------------------------------------
   Three-layer fallback:
     1. ProfileImageCache.resolve() — disk/memory cached bytes.
     2. NetworkImage(profile-image URL) with built-in
        errorBuilder/frameBuilder.
     3. CircleAvatar with Icons.person glyph.
   Critical: when bytes come back as a 1×1 transparent PNG (the
   server placeholder above), Flutter still treats it as a valid
   image and shows the white circle. NOT layer 3. By design.

IMPACT FOR P1.T15 — fallback behaviour is UNCHANGED
---------------------------------------------------------------
   The worker doesn't touch any of these paths. Until the worker
   completes, the student's OLD `profile_image` is still on disk
   and still returned. There is never a window where:
     - profile_image points to a non-existent file
     - the controller returns the placeholder instead of the avatar
   ⇒ The user sees the OLD avatar until the new one is ready, then
   sees the new one on the next refresh (cache-bust via ?v=<ts>
   ensures Flutter/browser doesn't keep stale bytes).

7. FLUTTER PROFILE-IMAGE USAGE
================================================================================

Where Flutter writes profile_image
---------------------------------------------------------------
   - Onboarding (lib/pages/onboarding_page.dart l. 51-58):
       POST /api/onboarding/complete  with
       body['profile_image'] = 'data:image/jpeg;base64,...'
   - Profile update flows (various profile-edit pages) hit
       POST /api/student-profile/update  with the same data URL.
   ⇒ Both go through the BASE64 paths (B and C). P1.T16 will move
     them through the queue.

Where Flutter reads profile_image
---------------------------------------------------------------
   - lib/widgets/profile_avatar.dart — the ProfileAvatar widget.
   - lib/services/profile_image_cache.dart — ProfileImageCache:
       Memory cache (web) + on-disk cache (mobile/desktop).
       Falls back through a list of candidate URLs from
       Student.profileImageNetworkUrlCandidates(apiBaseUri).
   - lib/models/student.dart l. 171-190:
       profileImageNetworkUrlCandidates() — builds the candidate URLs.
       Always tries `/students/<serverId>/profile-image` first when
       both serverId and a non-empty profile_image are known.
   - lib/services/student_profile_refresh.dart — periodic refresh of
       the current student's avatar after profile edits.

Compatibility contract with deployed Flutter APKs
---------------------------------------------------------------
   - The GET URL pattern `/api/students/{id}/profile-image` MUST
     remain stable.
   - The response MUST stay binary image bytes with the same
     Content-Type set (image/jpeg / image/png / image/webp).
   - The CORS header `Access-Control-Allow-Origin: *` MUST stay set.
   - The placeholder PNG (200 OK + 1×1) MUST stay the empty-state
     response — Flutter web depends on it for graceful failure.
   - The `?v=<timestamp>` cache-buster MUST stay on the URL produced
     by profileImageUrl() — Flutter relies on this to refresh.

   None of these contracts are touched by P1.T15. Confirmed safe.

POST contract for profile_image upload
---------------------------------------------------------------
   - POST /api/onboarding/complete
   - POST /api/student-profile/update
     - Continue to accept `profile_image` as base64 data URL.
     - Continue to return success/422 with the same JSON envelope.
     - Continue to use 422 (not 500) on a rejected image.
     - After T15+T16, success still means "the system accepted your
       image" — but the response is fired BEFORE the resize completes.
     - The user sees the new avatar on the NEXT pull-to-refresh
       (typical Flutter UX already does this). No client change needed.

8. STORAGE AND BANDWIDTH IMPACT
================================================================================

Storage delta
---------------------------------------------------------------
   Final disk usage: UNCHANGED. Same encoder, same cap, same path.
   Transient disk usage: + ≤ N * 5 MB on `storage/app/private/
   tmp-profile/` (N = number of in-flight jobs).
   On cPanel with the recommended cron-driven runner (1 tick / min),
   N is bounded by minute-scale upload concurrency — realistically
   < 20 MB transient at peak.

Bandwidth delta
---------------------------------------------------------------
   Inbound:  UNCHANGED (operator still uploads the same raw bytes).
   Outbound: UNCHANGED (avatars served from the same path with the
             same cache headers).
   Worker:   No outbound — worker only reads from disk.

Read-side cache headers (unchanged today and post-T15)
---------------------------------------------------------------
   StudentImageController emits:
     Cache-Control: public, max-age=86400
   Plus the controller's ?v=<updated_at-timestamp> cache buster on
   the URL. Result: browsers + Flutter cache the binary for a day
   and revalidate only when `updated_at` changes.

   IMPORTANT INTERACTION WITH T15: `updated_at` on the Student model
   changes when $student->save() runs in the worker (because the
   `profile_image` column was just updated and Eloquent touches
   `updated_at` automatically). The cache-buster value therefore
   flips at the same moment the avatar binary changes. ⇒ No
   stale-cache risk.


================================================================================
9. SHARED-HOSTING MEMORY CONSIDERATIONS  (cPanel target)
================================================================================

Worker availability
---------------------------------------------------------------
   cPanel hosts have NO long-running queue daemon. The Phase 7 plan
   uses a cron-driven runner:
     * * * * * cd /home/user/site && php artisan queue:work
       --once --tries=3 --timeout=60 --stop-when-empty
   This ticks every 60 s. The ResizeStudentProfileImage job's
   $timeout=60 fits inside one tick.

   IMPLICATION: until the operator deploys the cron line, the job
   row sits in `jobs` and the worker never runs. The student's
   image will only update after the cron line is in place. P1.T15
   spec calls this out (MIGRATION STEP 3: "Make sure
   QUEUE_CONNECTION is set (database is fine for Phase 1)") — but
   the cron line is a Phase 7 deliverable. We should document in
   the implementation commit message that a stop-gap MUST be in
   place before T16 ships.

Worker memory cost
---------------------------------------------------------------
   The worker (PHP CLI process) has its own memory_limit. On most
   cPanel hosts CLI memory_limit > PHP-FPM memory_limit (often
   256 MB vs 128 MB). Post-T16 the worst-case GD allocation is
   ~6.5 MB (1280x1280x4), so the worker can comfortably resize
   even multiple jobs per tick.

Worker concurrency
---------------------------------------------------------------
   Cron-driven runner = single worker, single tick. No concurrent
   GD loops competing for memory. ✓

Failure semantics
---------------------------------------------------------------
   - $tries=3: a transient GD failure (e.g. corrupted upload) is
     retried up to 3 times before landing in `failed_jobs`.
   - Each failure logs to laravel.log via Log::error.
   - The temp file is deleted on the LAST attempt (or earlier on
     "student gone / temp missing / raw empty") to prevent
     accumulation.
   - On terminal failure, the student keeps their OLD avatar.

cPanel disk-quota risk
---------------------------------------------------------------
   - storage/app/private/tmp-profile/ is tiny under normal load
     but unbounded under attack. The 5 MB guard from T16 caps the
     per-file ceiling. A 10 GB disk quota gets used up by ~2 000
     concurrent malicious uploads — out of normal-traffic range.
   - The Phase 8 cleanup job will prune anything older than 24 h.

OPcache / queue.payload caching
---------------------------------------------------------------
   The serialized job payload (in the `jobs` table) is < 2 KB
   (studentId, tempRelativePath, a small Laravel envelope). Adding
   the new job class does NOT meaningfully grow OPcache because
   Laravel's framework code (Dispatchable, Queueable, etc.) is
   already cached for SessionLiveEvent and AttendanceDataResetEvent.

10. ROLLBACK STRATEGY
================================================================================

Layer A — git revert (P1.T15 alone)
---------------------------------------------------------------
   Action     :  git revert <P1.T15 commit>
   Effect     :  Removes app/Jobs/ResizeStudentProfileImage.php and
                 the (empty) app/Jobs/ directory.
   Risk       :  Zero. Nothing dispatches the job until P1.T16 lands.
                 Worker queue stays empty.

Layer B — git revert when P1.T15 AND P1.T16 are BOTH deployed
---------------------------------------------------------------
   Action     :  git revert <P1.T16 commit> first; then optionally
                 git revert <P1.T15 commit>.
   Order rule :  T16 MUST be reverted BEFORE T15 — otherwise the
                 controller continues to dispatch jobs that no
                 longer have a handler class, which queues the
                 jobs and fails them on the next worker tick.
   Effect     :  saveProfileImageFromUpload() returns to the
                 synchronous GD path. saveProfileImageFromBase64()
                 returns to the synchronous GD path. Upload latency
                 returns to its pre-T15 baseline (~1-2 s on a 2 MB
                 JPEG). Memory exposure also returns. Use only
                 during incident response.

Layer C — drain pending jobs without rollback
---------------------------------------------------------------
   If T15+T16 land but the worker isn't ticking (e.g. cron line
   missing on a fresh deploy):
     php artisan queue:work --once --tries=3 --timeout=60 --stop-when-empty
   runs a single drain pass on demand. Safe to call from cPanel
   "Cron Jobs" → "Run Now" or from SSH. After the drain, fix the
   cron line.

Layer D — abandon pending jobs
---------------------------------------------------------------
   If the queue accumulates bad jobs (e.g. all 5 MB-cap rejected
   uploads from a single attack run):
     DELETE FROM jobs WHERE queue='default' AND payload LIKE '%ResizeStudentProfileImage%';
   then prune storage/app/private/tmp-profile/.
   Affected students keep their OLD avatars. No data loss.

Rollback ordering rule
---------------------------------------------------------------
   1. T15 alone   → straight revert. Zero side effects.
   2. T15+T16     → revert T16 FIRST, then T15 (or leave T15 alive
                    — the unused class is inert).
   3. Never delete app/Jobs/ResizeStudentProfileImage.php from a
      live host without first deleting the corresponding `jobs`
      rows; the worker will fatal on the missing class until you do.

       ls -ld storage/app/public/students 2>/dev/null

       * * * * * cd /home/<user>/public_html && php artisan queue:work \
         --once --tries=3 --timeout=60 --stop-when-empty

8. BACKWARD COMPATIBILITY RISKS
─────────────────────────────────────────────────────────────────────────

  CATEGORY A — Predicate behaviour
  ────────────────────────────────
  Risk:  PasswordPolicy::matches behaves differently from
         validateApiPassword.
  Reality: They are bit-identical functions today.
    validateApiPassword(input, stored):
        if empty(stored)        → false
        if stored startsWith $2y$/$2a$ → Hash::check(input, stored)
        else                    → input === stored
    PasswordPolicy::matches(input, stored):
        if stored is null/''    → false
        if isBcrypt(stored)     → Hash::check(input, stored)
        if config('auth.allow_plaintext_legacy_passwords') === true
                                → hash_equals(stored, input)
        else                    → false
  Severity: NONE during the migration window (P1.T01 default flag = true
            → PasswordPolicy is bit-identical to the deleted helper).
            After AUTH_ALLOW_LEGACY_PLAINTEXT=false is flipped post-rehash,
            plaintext rows lose access on these two endpoints just as
            they will across the rest of the app — that is the intended
            outcome of the whole Phase 1 stack.

  CATEGORY B — Response shape
  ───────────────────────────
  updateLocation (401 'Wrong password' branch):
    Risk:  body or HTTP status changes.
    Reality: P1.T05 leaves response()->json(['message' => 'Wrong password'], 401)
             exactly as-is; only the predicate above the `if` changes.
    Severity: NONE.

  active via missedWarningExtras:
    Risk:  the silent-empty fallback flips to a 401 or error.
    Reality: P1.T05 preserves the early `return [];` shape, so the
             outer 200 response (sessions only, no warnings) is
             unchanged for wrong-password callers.
    Severity: NONE.

  CATEGORY C — Flutter contract
  ─────────────────────────────
  Risk:  Flutter screens parse fields that get removed or renamed.
  Reality:
    - getActiveSessions parses only `sessions`, `warnings`, `warnings_map`
      (warnings keys remain optional, same as today).
    - rep_course.dart, session_attendance_payload.dart,
      rep_session_page.dart, attendance_page.dart all read fields built
      by ActiveSessionListBuilder, which P1.T05 does not touch.
    - There is NO Flutter caller for updateLocation; nothing to break.
    - There is NO Flutter caller for currentQr; out of scope anyway.
  Severity: NONE.

  CATEGORY D — Web blade / dashboard contract
  ───────────────────────────────────────────
  Risk:  a web admin page calls one of these endpoints and breaks.
  Reality:
    - No blade file calls /api/sessions/active (web admin uses
      AttendanceSessionController + ClassRepController routes directly).
    - No blade file calls /api/sessions/{id}/location (web admin sets
      session location during open via the rep web form).
    - No blade file calls /api/sessions/current-qr (rep QR page uses
      `dashboard.live-sessions.qr-payload` which is a different web
      route).
  Severity: NONE.

  CATEGORY E — External / Postman / v1 doc users
  ───────────────────────────────────────────────
  Risk:  Postman collection or external integrator depends on the
         legacy /api/sessions/active?include_missed_warnings=... shape.
  Reality:
    - docs/postman/at-nda-api-v1.postman_collection.json exercises
      /api/v1/sessions/active?include_missed_warnings=1, which goes to
      App\Http\Controllers\Api\V1\SessionController (different class,
      not in P1.T05 scope).
    - docs/API_V1.md documents the same v1 endpoint with Bearer auth.
    - The legacy /api/sessions/active path is undocumented for
      `include_missed_warnings`, so any external caller using it is
      relying on a documented-only-in-source contract.
  Severity: LOW for any such ad-hoc caller; the response shape is
            preserved verbatim, only the predicate changes (same
            migration-window behaviour as everywhere else).

  CATEGORY F — Race / state risk
  ──────────────────────────────
  Risk:  Removing the local predicate alters call ordering relative to
         AttendanceSession::deactivateExpiredSessions(), Sanctum, or
         model events.
  Reality: PasswordPolicy::matches is a pure function (no DB I/O, no
           model events). The order of operations inside updateLocation
           remains: validate → deactivate-expired → refresh → active-gate
           → student lookup → PASSWORD GATE → main-rep gate → write.
           Identical to today.
  Severity: NONE.

  CATEGORY G — Operational / audit risk
  ─────────────────────────────────────
  Risk:  Removing validateApiPassword breaks an internal log alert that
         greps for the literal method name.
  Reality: Searched the repo for log strings referencing
           "validateApiPassword". No matches in logs/, app/, or
           bootstrap/. The only references are in source files (helper
           definitions and call sites).
  Severity: NONE.
